Q1: FDB separates transaction management from storage so each layer can scale independently based on the workload. The TMS assigns versions, checks conflicts, and coordinates commits, with LogServers making the writes durable. The Storage System manages sharded, versioned data and serves client reads while applying updates from the logs in the background.
Q2: The Resolvers detect read-write conflicts between concurrent transactions. After the Proxy gets a commit version, the Resolvers check whether another transaction committed a write to any of the transaction’s read conflict ranges after its read version. This happens before the transaction’s mutations are sent to LogServers for persistence, and a detected conflict causes the transaction to abort.
Q3: The read version identifies the database snapshot that a transaction reads, keeping its reads consistent across different StorageServers. It is at least as recent as transactions that finished committing before this transaction started, so the snapshot respects real-time ordering. Combined with conflict checks at commit time, this supports FDB’s strict serializability guarantee.
Q4: Both types of reads use a consistent snapshot, but standard reads add read conflict ranges, while snapshot reads do not. I’d use standard reads when an update depends on what I read, like checking inventory before reducing it, because a concurrent change should trigger a retry. I’d use snapshot reads for an advisory lookup where a concurrent change would not affect the correctness of my update.
Q5: During normal operation, data is durably replicated using LogServers and StorageServers will continually consume and apply mutations. When a failure occurs FDB reads the LogServers to choose a safe recovery version and starts up a new transaction system. The StorageServers can continue to catch up asynchronously, allowing us to process new transactions without replaying the redo log first. This keeps recovery costs low as the log application process is already done during normal operations and as the Proxies and Resolvers are stateless there is no state to reconstruct.
